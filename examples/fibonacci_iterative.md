## LLM review

## Summary
The Weave compiler toolchain successfully compiles `examples/fibonacci_iterative.weave` into correct and efficient native code. The Weave source defines an iterative Fibonacci function and a `main` entry point that returns `fib(10)`. The WIR preserves the source semantics accurately. The raw LLVM IR generated by weavec is valid SSA, though it uses a straightforward stack-based alloca-and-load/store strategy for local variables. LLVM's optimization passes (as shown in the optimization record and optimized LLVM IR) successfully promote these memory locations to registers, inline the `fib` call into `main`, and constant-fold the computation. The final linked executable disassembly confirms that `main` simply returns the constant `55` (`0x37`) via `movl $0x37, %eax; retq`, which is the correct result for `fib(10)`. The `fib` function itself is preserved as a clean, register-based loop in the native code. No merge-blocking defects were observed.

## Blocking findings
None found.

## Non-blocking opportunities
- **Raw LLVM IR verbosity**: The raw LLVM IR for `fib` uses `alloca` for `prev`, `curr`, and `i`, resulting in repeated `load` and `store` operations inside the while loop. While LLVM's `mem2reg` pass completely optimizes this into SSA registers in the optimized LLVM IR (and the final native code contains no stack traffic for these variables), weavec could potentially generate more direct SSA-based IR upfront. This is a non-blocking compiler implementation detail that does not affect the final executable's performance or correctness.
- **Loop vectorization**: The optimization record notes that the loop in `fib` was not vectorized. This is expected for a recurrence relation like Fibonacci where loop iterations are dependent on previous results. This is a non-blocking architectural characteristic of the source algorithm.

## Suggested verification
- **Boundary condition tests**: Add test cases for `fib(0)` and `fib(1)` to explicitly verify the early exit condition (`le_i32 n (const_i32 1)`) in the native assembly.
- **Large input tests**: Test `fib(n)` with a larger `n` (e.g., `n = 90`) to ensure the iterative loop scales correctly and to observe the loop's performance characteristics in the generated native code.
- **Overflow behavior**: If Weave is intended to support defined behavior on integer overflow, adding a test for `fib(n)` where `n` is large enough to cause `i32` overflow (e.g., `n > 46`) would verify the compiler's handling of `add_i32` wrapping.
