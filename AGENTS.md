# Agent instructions

This repository regularly receives pull requests authored by autonomous
coding agents (branches named `agent/*`), and reviewing and merging them is
itself often done by an agent. This file captures how to do that well here,
in addition to the human-facing rules in CONTRIBUTING.md.

## Reviewing and merging a PR

1. Read the diff and commit history (`gh pr view <n>`, `gh pr diff <n>`).
   Check CI (`gh pr checks <n>`) but don't stop there — read the actual
   security- and correctness-critical code yourself.
2. Test locally in a worktree: `uv sync --group dev`, then `ruff check .`,
   `ruff format --check .`, `mypy`, `pytest`. Compare against CONTRIBUTING.md.
3. Before merging, rewrite the branch's commit history to follow
   CONTRIBUTING.md's commit rules: squash commits that were never
   independently revertable (iterative `fix:` chains correcting a mistake
   introduced earlier in the same PR, `style:` formatting fixups, a stale
   pre-existing test assertion that needs updating for a message your commit
   changed). Group by logical story, not by the order the agent that wrote
   the PR happened to commit in.
4. Verify the rewritten branch's tree is byte-identical to the original PR's
   diff, file by file, before pushing (aside from any intentional fix you
   made). Only commit boundaries should move.
5. Push the rewritten history to the PR's existing head branch with
   `--force-with-lease` and let CI re-run.

## Two gotchas specific to this workflow

- **`--force-with-lease` "stale info" false positive:** if you only fetched
  the PR via `refs/pull/<n>/head` (not its actual branch name), your local
  remote-tracking ref for that branch doesn't exist yet, so
  `--force-with-lease` has nothing to compare against and rejects the push
  even though nothing changed remotely. Run `git fetch origin <branch-name>`
  once first.
- **Generated audit reports conflict across PRs:** `docs/audit/*.md` and the
  audit timestamps/hashes inside `*.audit.json` sidecars are regenerated by
  the `weave-audit` workflow after a passing verdict. If two open PRs both
  touch these files, rebasing the second one onto the first's merge will
  conflict in exactly these files. Don't hand-resolve that conflict — drop
  the stale generated-file diff, push the real code changes, and wait for
  the workflow to add its own "docs(audit): update generated reports" commit
  before merging. Hand-splicing generated diffs risks committing report
  content the tool never actually produced.

## Local environment caveat

This project's sandboxed native runtime execution (`runtime_sandbox.py`)
depends on a `bwrap` build recent enough to support `--clearenv` (roughly
bubblewrap 0.8+). Older systems only have bubblewrap 0.4-0.6, which will fail
`test_bubblewrap_hides_host_files_and_network` locally with `bwrap: Unknown
option --clearenv`. GitHub's runners have a new enough bubblewrap, so this is
a known local-only gap, not a merge blocker — confirm the PR's actual CI is
green rather than treating a local failure like this as a defect.

## Merging

Merge via `gh pr merge <n> --rebase --delete-branch` once CI is green on the
rewritten history and `mergeStateStatus` is `CLEAN`. This preserves the
cleaned-up commit boundaries in `master` instead of squashing the PR into one
commit.
